### M1 — data contracts and persistence ✅
- `models.py` implements every §4.1 object with validators: an unknown assessment has `judgment=None`; a known assessment must cite evidence; an LLM inference can never be a verified observation; a live `QueryResult` needs the run binding while a fixture one must have none; `Answer` epistemic rules; a `ResearchSpec` with branch `auto` is refused.
- `store.py`: SQLite is the single source of truth, using `BEGIN IMMEDIATE` transactions. An event is written in the same transaction as each state change. Records are append-only except a small set of mutable kinds, and a `CandidateRevision` key-field change is refused. Evidence is de-duplicated by (source, version, locator, content hash), actions by input fingerprint. There is a run lock with stale-lock takeover, migrations, JSONL export, and a WAL checkpoint on exit.
- Tests: T03 and T04; the resume tests T11.

### M2 — providers and literature ✅ (live LLM not verified)
- `agents/binding.py`: `ModelBinding` (requested product, `gpt-6-astra`, `reasoning_mode=pro`, `requested_effort=None`, SDK version, mapping date and sources, mapping check, binding hash, runtime metadata). The mapping check records the SDK's own declarations: SDK 3.59.0 lists `gpt-6-astra`, lists no `gpt-6-pro` id, and declares `Reasoning.mode: 'standard' | 'pro'`. It also records the web/account re-check result, which here is `ProxyError` with no key.
- `agents/providers.py`: the Responses request is assembled in one place (`model`, `reasoning={"mode":"pro"}`, developer/user input, JSON schema, `max_output_tokens`, no `effort`). The provider fails with `BINDING_MISMATCH` if the response reports another model or mode. Errors are mapped to `MISSING_CREDENTIALS / AUTH_FAILED / MODEL_UNAVAILABLE / PRO_MODE_UNAVAILABLE / RATE_LIMITED / TIMEOUT / NETWORK`.
- `agents/gateway.py`: the single call path. It reserves calls, input and output tokens (and USD when priced) before each call, retries a bounded number of times with the same model, charges failed attempts, and labels fixture usage as `fixture`.
- `FixtureProvider` never imports a network client. `offline_local` is refused for any non-fixture provider at config load and runs under `forbid_network()`.
- `literature/`: an arXiv provider (live), an OpenAlex provider (unverified), PDF page units via pypdf, HTML section units, import from a local file, URL, arXiv URL/ID or DOI, a search cache, budget accounting for searches and full-text reads, and canonical-id de-duplication.

### M4 — decision loop and resource control ✅
- `decision/ranking.py`: partial ranking with `insufficient_evidence`, ties and trade-offs. `personal_fit` breaks a tie on the science dimensions only under `personalized_loop`, and when it does the ranking is flagged as preference-sensitive.
- `decision/rules.py`:
  - **Vetoes:** an applicable, verified refutation, or verified coverage on every claim. Support counts never outweigh a refutation, and missing evidence is never a veto.
  - **Gates:** the §6.4 gates.
  - **Stop rules:** the §6.5 exits.
  - **Next action:** the §6.3 priority heuristic. It is explicitly not a Bayesian value-of-information computation.
- `controller.py`:
  - Explicit phase state machine; rounds alternate between assess and acquire_evidence.
  - The Q5 next-action proposal is validated in code: allowed type, existing unknown, active revision, and not a duplicate of an earlier action, a budget-refused input or a retry over the limit.
  - Actions are idempotent through their fingerprints; budget is reserved and settled atomically per attempt.
  - Revisions are immutable; old evidence is linked to a new revision only as `inconclusive` pending a re-check.
  - A checkpoint is written after every phase and round, and a status line is printed at most every 30 s.

## 3. Design decisions

1. **Location.** The package lives in the existing `auto-research` repository on branch `GPT-version`. The earlier Claude Code skill (`.claude/`, `research/`) is kept unchanged, and its README moved to `docs/claude_code_skill.md`. The plan's default stack (Python, Pydantic 2, Typer, SQLite, PyYAML, httpx, pytest) is used. No existing component offered an equivalent controller or store, so none was reused. The earlier Scholar listing is cited only as profile provenance (metadata only).
2. **Queries are actions** (idempotent and logged) but are charged to `llm_calls`/tokens, not to `max_actions`. `max_actions` counts research actions: pilots, searches, theory checks and backend runs.
3. **Fixture token accounting.** A reservation uses an upper estimate of about 2 characters per token; the fixture's "actual" usage is about 4 characters per token and is labelled `fixture`. It is never treated as a real call or a cost.
4. **Research outcome.** Formal claims decide it. For a theoretical candidate, a pilot counterexample is a real disproof and counts. For empirical or mixed candidates, pilot findings are reported but `research_outcome` stays `not_run`.
5. **Coverage veto.** It applies only when Q4 reports every claim covered and each covered claim cites literature read beyond the abstract. When the evidence is fixture data, the reason says so.
6. **Interrupted attempts** are charged at their reserved amount (conservative, never free). A pilot that finished before the crash is recovered from its marker and not recomputed.
7. **Protocol versions** are unique per `protocol_id`, so a revised candidate gets `@2`.
8. **The gates require live nearest-neighbour reading,** so an offline run can never recommend formal research. This is deliberate: fixture literature cannot justify research investment.
10. **User-approved model override (2026-11-27).** The user chose `gpt-6.2-astra` for the front end. `llm.model` must still be `gpt-6-astra` unless `llm.user_model_override: true` and a non-empty `llm.override_reason` are set. The override keeps one model per run, Pro mode, no effort and no fallback. The `ModelBinding` records `mapping_check.model_choice = "USER OVERRIDE, not the documented GPT-6 Pro mapping: …"` and `source = "config.llm (user model override)"`. This deviates from plan §2.1, which keeps `gpt-6-astra` as the documented mapping; whether `gpt-6.2-astra` accepts `reasoning.mode=pro` is decided by the API at call time (an unsupported mode fails as `PRO_MODE_UNAVAILABLE` / `BINDING_MISMATCH`).
11. **First live runs (2026-11-27, user's server, `gpt-6.2-astra` + Pro).** The first real call returned after about 2 minutes (about 18k input and 11k output tokens). Live use exposed and fixed four issues:
    - `task:<id>` input references were not resolvable;
    - there was no progress output during long calls: calls now run in Responses background mode with polling, a heartbeat every 30 s and cancellation at `request_timeout_seconds`;
    - a failed run could not be reopened: added `pra resume --retry-failed`;
    - frozen budgets could not be raised: added `pra resume --raise-limit KEY=VALUE`, which only increases limits, records each change and reopens runs stopped for budget or rounds.
9. **v3 paper phase.** In native mode it runs in Docker (`container.paper_enabled=true`), because upstream refuses native agents for the paper audit.
